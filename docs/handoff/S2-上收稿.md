## 给管家的话

建议把下面「建议补进 skill 的段落」并入 `android-fgs-long-audio-local-zh`，作为机制二强制检查。

理由：现有 skill 已经覆盖「锁屏长音频 + 前台服务 + wakelock 必须成对」这条主干，但它对 wakelock 的表述停留在「队列开始时获取」，没有回答一个更容易翻车的具体问题——**`setWakeMode` 不等于持续播放**。本轮项目就是照着「有 FGS、有 setWakeMode、锁屏也在播」的认知写的，结果锁屏后音频只前进约 95 秒就 PAUSED，而计时器照走满 180 秒并把一条「完成」写进历史。这属于 skill 当前防不住的假 PASS：现象层看起来「锁屏能播」，证据层却能拆穿它。补这一条不需要重写 skill，只需在硬约束与取证口径之间加一节判定法。

## 实测事实

**0.2.2 现象（缺陷）**
- 设备锁屏，跑 3 分钟（180 秒）计时任务。
- 音频实际只前进约 95 秒后转为 PAUSED（起点 132,885 ms，停在 230,844 ms）。
- 计时器不受影响，仍走满 180 秒，并按「完成」写入历史。
- 即：业务侧判定成功、听觉侧已中断，两者不一致，且不一致不可见。

**0.2.3 修复**
- 新增 `PlaybackHoldPolicy`：以 `playWhenReady` 为真 **且** 播放器处于解码/出音状态时持有 `PARTIAL_WAKE_LOCK`；暂停、停止、空闲、出错与服务销毁时释放。
- `PlaybackService` 同步切换前台状态，使「前台存活」与「真的在出声」两件事对齐。
- 关键点：锁的持有条件由**播放状态**驱动，不再依赖播放器自带的 wakeMode 行为。

**0.2.3 复测**
- 锁屏全程 `dumpsys power` 为 `mWakefulness=Asleep`（确认是真熄屏，不是变相亮屏）。
- 断点 230,739 ms → 410,587 ms，差值 179,848 ms，约等于 180 秒。
- `timer_sessions` 记为 180 秒完成。
- 界面进度 26% → 81%，与断点毫秒差一致。

## 建议补进 skill 的段落

以下为可直接粘贴的 Markdown（建议放在「七条硬约束」之后、「取证口径」之前）：

```markdown
## 机制二：setWakeMode 不等于持续播放

**只设 `setWakeMode(context, PARTIAL_WAKE_LOCK)` 不够。** 它表达的是「播放期间希望保持 CPU」，
是否真的保持取决于播放器内部状态机：暂停、缓冲耗尽、出错、队列间隙、引擎重建时都会被放开；
自写引擎（TTS 队列、自定义解码循环）常常根本没把 wakelock 挂上去。表现是「锁屏后播了几十秒就停，
但计时/进度照走」——业务判定成功，耳朵判定失败。

**按状态持锁（判据）**

- 持锁条件：`playWhenReady == true` **且** 播放器状态 ∈ `{STATE_READY, STATE_BUFFERING}`
  （或引擎自报「正在解码/正在出音」）。
- 释放条件：`STATE_IDLE` / `STATE_ENDED`、用户暂停、队列清空、出错、`onDestroy`、服务被回收。
- 状态切换与持锁/释放必须是同一处代码驱动（策略类或状态回调），不得在多个入口各写一遍。

**必须成对释放**：正常结束、用户停止、失败、异常回调、服务销毁五条路径都要释放；
释放要幂等（重复调用不抛异常），持锁计数不得累积。播完还持着 = 泄漏，会耗电并被投诉。

**真机验收判定法（三方交叉，缺一不算 PASS）**

1. 起止断点毫秒差 ≈ 设定时长（如 179,848 ms ≈ 180 s）；
2. 业务表/时间线里该任务记为完成（如 `timer_sessions` 180 秒）；
3. 界面进度与上面两者对得上（如 26% → 81%）；
4. 全程 `mWakefulness=Asleep`。

**禁止**只拿一次 `dumpsys power` 快照就下结论——快照只能证明那一瞬间持着锁，
证明不了全程没断。快照是旁证，断点差 + 完成记录 + 界面进度才是主证。

**固定回执**

```text
【锁屏播放回执】
锁屏时长: <设定秒数>；实际播放: <起止毫秒差> ≈ <秒>
唤醒态: mWakefulness=<Asleep/其他>（全程采样 <n> 次）
持锁: <策略类名> 按 playWhenReady+STATE_READY/BUFFERING 持有；释放点 <列表>
三方交叉: 断点差 <ms> / 业务记录 <表名+值> / 界面进度 <a>%→<b>%
结论: PASS / FAIL
未验证: <列出没测到的项，如耳机拔出、来电中断>（不得填 PASS）
```
```
