# 并发派工轮询门禁（上收稿）

> 用途：把「派工后必须自己轮询到完工」并入相关用户级 skill，作为机制二强制步骤。
> 目标 skill（任选其一或全部）：`dispatch-verify-loop-local-zh`、`codearts-parallel-local-zh`、`codebuddy-parallel-local-zh`。
> 来源：069 项目 2026-11-12 实测——CodeBuddy 派工后日志 0 字节、进程仍在、版本号已改但 APK 未重出，靠人工查 `ps` 与 APK mtime 才发现。

## 给管家的话

建议把下面「轮询门禁」段并入上述 skill，作为并发派工后的强制步骤，并要求收尾贴固定回执；缺失回执不算完成。理由：现有多路派工只规定启动与错峰，没有规定派工方必须持续观测，遇到「进程活着但零输出」时会被误判为正在工作，白等十几分钟。

## 建议补进 skill 的段落

```markdown
## 派工后轮询（机制二，缺回执不算完成）

1. 派工前记录基线：目标产物路径与 mtime、启动时间、进程标识。
2. 每 60–90 秒检查三项：进程是否存活、日志字节数是否增长、目标产物 mtime 是否变化。
3. 日志 0 字节或三项静止超过 10 分钟，判停滞：结束该路进程，再决定拆分重派或改由主线程完成；不得原样重派第二次。
4. 进程退出后回读产物（存在、版本、大小、SHA、关键数字、测试通过数），不得只看退出码或自报列表。
5. 禁止用本机看门狗/定时自动化替代人工轮询；禁止两路同时写同一文件。

收尾必须附：
【并发轮询回执】
- 路 A：<起止时间 / 进程数峰值 / 日志字节变化 / 产物 mtime 与 SHA / 退出码>
- 路 B：<同上>
- 停滞处置：<无 / 哪一路第几分钟判停及动作>
- 结论：<ALL_DONE / PARTIAL / BLOCKED>
```

## 待管家决定

2. 是否把「停滞 10 分钟」阈值写成可配置项。
3. 是否要求回执强制输出，与现有 PASS/PARTIAL 判定合并。
